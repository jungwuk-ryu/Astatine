# 밀집 지역 성능 개선 및 배포 검증

## 구현과 선택 근거

- 이동 중 방문한 블록 집합을 스레드별로 재사용한다. 중첩 방문은 별도 집합을 사용하고, 조기 종료/예외에서 반환하며 큰 집합은 보관하지 않는다. 빈 블록 효과 목록 복사도 제거했다.
- 끼임 피해 규칙이 꺼진 경우에만 충돌 후보를 실제 충돌 제한까지 조회한다. 처리 순서, 팀 규칙, 자기 자신 제외, 멀티파트 경로를 유지한다. 끼임 피해가 켜져 있으면 전체 개수 조회를 유지한다.
- 작은 이동/회전/속도 패킷을 연결별 최대 64개 작업으로 묶는다. 패킷 바이트는 수신자마다 인코딩하므로 PacketEvents/ProtocolLib의 수신자별 변환을 보존한다. 전체 송신 큐가 64개로 제한된다는 뜻은 아니다. Netty MPSC 큐에 직접 넣고 연결마다 소비 작업 하나만 예약한다. 콜백, 일반 전송, 명시적 flush, 프로토콜 전환, 종료는 큐 순서를 보존하며 일반 작업 뒤에는 다른 연결에 실행 기회를 준다.
- 독립 틱에서는 전역 suspend/resume 대신 실제 지역 추적 단계에 flush 범위를 둔다. 긴 추적 중에는 약 1ms 간격으로 활동 시 flush하며, 단계 종료/예외에서도 flush한다. 1ms 네트워크 지연 보장을 뜻하지 않는다.
- 소유한 락이 없는 작업자의 전체 락 맵 순회를 없앴다. 별도 소유 개수로 고아 락 복구 경로를 유지한다. 이미 게시된 저장 데이터는 캐시에서 바로 읽고, 최초 생성만 원자적으로 수행한다.
- 락 실패는 최초 기록된 예정 시각과 실패 횟수를 재시도 사이에 유지하는 JFR 요약 이벤트로 기록한다. 확인한 차단 셀/스레드는 관찰 시점의 정보이며 소유권 판단에 사용하지 않는다.

같은 지역의 엔티티 상태를 동시에 수정하는 구조와 보호 영역 축소는 채택하지 않았다. 측정에서 비용이 컸던 송신 연산은 이미 Netty가 병렬 처리하므로, 새 스냅샷/워커/적용 단계를 더하기 전에 작업 객체·큐 등록·할당 비용을 줄이는 방식을 구현했다. 기존 비동기 길찾기의 지역 안전성 제한도 유지한다. 첫 대조 실행에서는 지역 샘플 3,224개 중 길찾기가 49개(1.5%), 추적·송신이 1,024개(31.8%)였다. 이는 새 길찾기 워커를 우선 도입할 근거가 약하다는 뜻이며, 주민이나 적대 몹의 AI 부하까지 판단한 결과는 아니다.

## 채택하지 않은 결과와 비교 범위

첫 배열/모니터 기반 전송 큐(aea4caf)는 할당과 GC는 줄었지만 동일한 80명/240마리 대조에서 p95가 36.0ms에서 62.0ms로 늘었다. 새 큐의 모니터 경합도 기록됐다. 이 아티팩트는 운영에 배포하지 않았으며, 생산자 모니터가 없는 최종 MPSC 큐로 교체했다. 두 실행의 공유 호스트 부하도 달라 지연 차이 전부를 모니터 탓으로 단정하지 않는다.

별도의 큐 비활성화 실행과 압축을 켠 기존 빌드의 80명 실행은 keepalive 시간 초과로 수락 조건을 충족하지 못했다. 연결 종료 후 지역이 비어 빨라진 기록을 개선 근거로 사용하지 않았다. 최종 비교는 운영 정원 45명에 가까운 40명과 소 240마리로 양쪽을 다시 실행했다.

최종 두 압축 조건은 GraalVM 25, 지역 작업자 7개, cramming 24, 충돌 제한 2, heap 2–4GiB, ActiveProcessorCount 7을 공유한다. 첫 쌍은 압축 임계값 128이며 후보에만 진단 카운터를 켰다. 두 번째 쌍은 운영 압축값 512이며 양쪽 진단 카운터를 끄고 실행 순서를 뒤집었다. 각 실행은 새 격리 월드, 전체 클라이언트 상호 가시성, 190회 연결 검사, 전후 소 240마리, 정상 종료를 요구했다.

실운영의 heap 2–16GiB, 시야 18/시뮬레이션 거리 4, keepalive 180초와 달리 비교는 heap 2–4GiB, 시야/시뮬레이션 거리 2, keepalive 30초를 사용했다. 같은 호스트의 다른 작업은 중단하지 않았다. 이 비교는 평화 모드 소와 합성 이동 부하이며, 전체 운영 플러그인·적대 몹 AI·주민·WAN·네이티브 클라이언트 FPS를 재현한 수치는 아니다. JFR 샘플 비율은 전체 CPU 시간 비율로 해석하지 않는다.

압축 128 조건은 양쪽이 모두 통과했다. 압축 512 조건에서는 새 빌드는 통과했지만 기존 빌드가 162/190회 시점에 일부 연결의 keepalive 시간 초과로 실패했다. 전후 몹 수는 유지됐지만 전체 연결 계약을 만족하지 못했으므로 이 기존 빌드 실행의 성능 숫자는 제외했다. 새 빌드가 같은 두 조건에서 통과했다는 사실과 실패 원인이 확정됐다는 주장은 구분한다.

| 압축 128, 40명 + 소 240마리 | 기존 빌드 | 최종 큐 구현 |
| --- | ---: | ---: |
| 지역 틱 중앙값 | 19.89ms | 15.38ms |
| 지역 틱 p95 | 32.44ms | 29.74ms |
| 지역 틱 p99 | 40.52ms | 36.69ms |
| 지역 틱 최대 | 177.68ms | 70.45ms |
| 지역 스레드 할당 | 33.70MB/s | 20.08MB/s |
| Netty 스레드 할당 | 22.15MB/s | 31.64MB/s |
| 위 두 그룹 합계 할당 | 55.85MB/s | 51.71MB/s |
| 60초 JFR의 GC 정지 합계 | 392.54ms | 74.98ms |
| JFR의 평균 JVM CPU 부하 | 34.87% | 14.94% |
| 같은 구간 호스트 전체 CPU 부하 | 99.12% | 68.98% |

CPU 부하는 JFR이 보고한 정규화 값이며 JVM 컴파일/GC도 포함한다. 호스트 부하가 달랐고 짧은 비교이므로 수치를 보장된 개선율로 해석하지 않는다. 두 번째 새 빌드 실행(압축 512, 진단 꺼짐)은 중앙값 10.44ms / p95 21.65ms / p99 28.82ms / 최대 33.86ms였지만, 완주한 기존 빌드 대조가 없어 이 조건의 개선율은 제시하지 않는다.

첫 새 빌드 실행의 진단은 이동 관련 패킷 18.16M개를 922,191개의 소비 작업에서 처리했다. 작업당 평균 19.69개, 작업 등록 후 실행까지 평균 0.777ms / 최대 46.54ms였다. 관측된 예약 소비 작업은 최대 40개로 연결 수와 같았다. 대기 패킷은 관측 최대 11,729개였으며 전체 큐를 제한한 것은 아니다. 이 값은 동시 갱신 카운터의 1초 간격 관측이고 패킷 RTT가 아니다.

## 실제 런타임 클래스의 메서드 검사

각 JAR에서 추출된 클래스를 별도 JVM으로 직접 실행했다. 각 조건은 20,000회 준비 실행 후 5,000회씩 9개 샘플을 기록했다. 벽시계 대신 현재 스레드 CPU 시간과 할당 바이트를 사용했다. 전체 서버의 처리량 실험은 아니다.

| 호출당 중앙값 할당 | 기존 | 최종 |
| --- | ---: | ---: |
| 이동 중 블록 방문 | 2,048B | 1,184B |
| 빈 블록 효과 수집기 처리 | 192B | 32B |
| 락이 없는 작업자의 정리, 외부 락 0개 | 568B | 0B |
| 같은 정리, 외부 락 512개 | 12,728B | 0B |

외부 락 512개에서 빈 작업자의 정리 CPU 시간은 약 10.69µs에서 0.208µs였다. 보호 영역 겹침 검사는 기존과 동일하게 인접 거리 1·2에서 두 번째 획득을 거부하고 거리 3에서 허용했다. 락 획득/해제 자체가 전반적으로 빨라졌다고 주장하지 않는다. 1셀 획득/해제의 관측 중앙값은 2.32→2.78µs였으며, 64셀은 36.74→36.40µs였다. 이번 락 변경의 대상은 무소유 작업자의 불필요한 전체 순회와 할당이다.
