# Eartopia Current 0.1.0-experimental 평가

2026-09-19, ShreddedPaper/Astatine 1.21.11, OpenJDK 25.0.2.

## 판정: 이번 버전의 운영 도입 보류

큐 구현의 정확성과 현재 소스에 대한 적용 가능성은 확인했다. 그러나 현재 JVM과
실제 노드 객체에서 성능 우위가 일관되지 않았고, 전체 레드스톤 엔진의 CPU/MSPT
개선 및 실제 회로/플러그인 호환성은 검증되지 않았다. 기본 큐를 교체할 근거가
충분하지 않아 기존 Alternate Current를 유지한다. 서버 소스 패치와 운영 배포는 하지 않았다.

이는 기능 오류가 발견됐다는 판단이 아니다. 단일 원소 처리의 이득은 재현되므로
최적화 후보로서의 가치는 있다. 실제 회로의 큐 작업 분포와 전체 처리 시간을 측정한
후 다시 판단할 수 있다. 측정하지 않은 보조 최적화도 채택하지 않는다.

## 범위

사용자가 제공한 `Archive.zip`의 큐 교체를 검토한 독립 검증 도구다.
이 디렉터리는 서버의 main/test source set에 포함되지 않는다.
`BucketedPriorityQueue`는 첨부 구현 그대로이고, 서버의 `WireHandler`에는
연결하지 않았다. 실행 플래그나 운영 설정도 추가하지 않았다.

첨부 패키지가 기준으로 삼은 [Paper 커밋](https://github.com/PaperMC/Paper/commit/c5eb0790f199da6c38d0a650e1e5cd5415b28185)과
[Alternate Current 원본 프로젝트](https://github.com/SpaceWalkerRS/alternate-current)를 확인했다.
현재 checkout의 `PriorityQueue.java`는 첨부의 비교 원본과 바이트 단위로 일치한다.
첨부 ZIP, 현재 큐/노드 소스 및 평가에 사용한 서버/API JAR의 해시는
`SOURCE_LOCK.json`에 기록했다. 패키지 및 파생 테스트의 MIT 고지는 `LICENSE.txt`에 보존했다.

## 정확성과 적용 가능성

- 첨부 SHA256 목록 중 존재하는 55개 파일은 모두 일치했다. ZIP에는 목록에 있는
  `.github/workflows/ci.yml`, `.github/workflows/paper-build.yml`, `.gitignore`가 없다.
  첨부 설명의 CI 실행 가능 여부는 이 ZIP만으로 확인할 수 없다.
- 원본의 대역 Node 테스트를 재실행했다. 500만 무작위 연산, 100,000개 짧은 연산열,
  24,576개 우선순위/삽입 순열, 2,816개 벤치마크 입력 사이클 및 Python 검사 5개가 통과했다.
- 같은 차등 모델을 현재 서버의 **실제 `Node`와 `WireNode`**로 다시 검사했다.
  생성자와 실제 `priority()`를 사용하며 Node를 상속한 대역은 없다.
  동일한 500만 연산, 100,000개 연산열, 24,576개 순열 및 2,816개 입력 사이클이 통과했다.
- 높은 우선순위 우선, 동일 우선순위 FIFO, 중복 등록, 우선순위 변경 후 뒤에 삽입,
  요청 우선순위와 등록 우선순위 분리, poll/clear 후 링크 해제, 빈 큐 재사용을 검사했다.
  독립 모델과 원본 큐를 함께 비교했으며 내부 링크/버킷 상태도 검사했다.
- 첨부 패치는 현재 생성된 Minecraft 소스에서 `git apply --check`에 통과했다.
  별도 디렉터리에서 패치를 적용한 5개 클래스의 Java 25 컴파일도 성공했다.
  **이는 전체 서버 Gradle 빌드 성공을 뜻하지 않는다.**
- 현재 ShreddedPaper의 핸들러는 `ServerLevel`의 `ThreadLocal`이다. 후보 큐도
  핸들러별 인스턴스로 만들면 기존 접근 범위를 유지할 수 있다. 이 큐 자체에는
  스레드 안전성이나 교차 region 전달 기능이 추가되지 않는다.

이 검증은 월드 접근, 이벤트 콜백, 피스톤/관측기/비교기 회로 실행을 포함하지 않는다.
큐 처리 순서의 일치와 실제 회로 호환성을 구분해야 한다.

## 성능 측정 방법

첨부와 동일한 작업을 대역 Node로 실행한 Java 25 결과는
`results/fixture-java25/`에 보존했다. 한 JVM에서 여러 작업을 순차 실행한 실제 객체
탐색 결과는 `results/actual-grouped-exploratory/`에 보존했다. 후자는 실행 순서에
따른 편차가 커서 최종 판단의 수치로 사용하지 않는다.

최종 비교는 실제 객체를 사용하고 **작업/구현/반복마다 독립 JVM**을 실행한다.
WireNode와 일반 Node를 번갈아 생성한다. 일반 Node의 `neighborWire`와 WireNode의
`virtualPower`를 통해 실제 우선순위 계산을 호출한다. 입력 객체 생성과 Minecraft
레지스트리 초기화는 측정에서 제외한다. 월드나 실행 중인 서버에는 연결하지 않는다.

AC/EC 한 쌍은 같은 CPU에 고정하고 실행 순서를 교차한다. 작업마다 3쌍의 JVM,
JVM마다 3초 워밍업과 300ms 샘플 5개를 사용한다. 비교 기준은 각 JVM 샘플의
중앙값을 구한 뒤, 그 중앙값 3개의 중앙값이다. `ns/cycle`은 작업 한 사이클의
시간이며 블록당 시간이나 MSPT가 아니다. 입력 우선순위 설정과 결과 체크섬 비용도
양쪽에 동일하게 포함한다. 공유 호스트의 마이크로벤치마크이며 JMH/서버 용량 증명이 아니다.

## 독립 JVM 최종 결과

실제 객체, 5개 작업 × 2개 구현 × 3개 JVM × 5개 샘플 = **150개 샘플**.
변화율이 양수이면 후보가 더 느리다. 마지막 열은 같은 반복의 AC/EC 중앙값으로
계산한 변화율 3개를 실행 순서대로 표시한다. 서로 다른 반복을 독립 표본 15개로
취급하지 않았다.

| 작업 한 사이클 | 기존 AC (ns) | 후보 EC (ns) | 중앙값 기준 시간 변화 | 각 반복의 시간 변화 |
|---|---:|---:|---:|---|
| 단일 삽입·제거 64회 | 1,617.6 | 1,023.5 | -36.7% | -36.7%, -31.6%, -38.2% |
| 동일 우선순위 64개 | 727.3 | 880.7 | **+21.1%** | +9.4%, +21.9%, -35.9% |
| 우선순위 내림차순 16개 | 253.4 | 244.9 | -3.3% | +1.5%, -3.3%, +52.9% |
| 혼합 우선순위 256개 | 5,221.0 | 4,717.5 | -9.6% | -9.5%, -9.6%, -50.2% |
| 삽입·제거 교차 | 12,993.8 | 9,767.9 | -24.8% | -4.9%, -34.9%, -17.8% |

동일 우선순위 작업은 3회 중 2회 느렸고 1회 빨랐다. 후보가 항상 느리다고
단정할 수 없으며, 모든 회로에서 빨라진다는 근거로도 사용할 수 없다.
큰 이득이 나온 작업의 배율을 서버 전체에 적용하거나 작업별 비중 없이 단순 평균을
내지 않는다. 특히 같은 우선순위의 이웃 업데이트는 실제 핸들러에서도 발생하므로
단일 원소 작업의 이득만으로 기본 교체를 결정하지 않았다.

양쪽 모두 측정 구간의 할당량은 0.0 bytes/cycle이었다. 후보의 추가 head 배열은
큐 생성 시 할당되므로 이 수치가 큐 인스턴스의 메모리 사용량이 같다는 뜻은 아니다.

원시 값과 환경/소스 해시는 `results/actual-independent/`에 있다.
기능 검증 요약은 `results/validation.json`, 실제 객체 검증 로그는
`results/actual-independent/validation.log`에 있다. 불리한 결과와 실행 순서에 민감했던
탐색 측정도 삭제하지 않고 보존했다.

도입 재검토에는 동일 테스트 월드에서의 AC/EC 회로 및 이벤트 순서 비교,
관측기/피스톤/비교기·청크/region 경계·이벤트 재진입 검증, 충분히 워밍업한 서버에서의
레드스톤 CPU 및 전체 MSPT p50/p95/p99 비교가 필요하다. 이번 결과를 그 검증의
대체물로 보지 않는다.

## 재현

Java 25, Python 3 및 Linux `taskset`이 필요하다. 현재 checkout의 Minecraft 소스가
생성되어 있고, 동일 버전 서버/API JAR와 런타임 라이브러리가 있어야 한다.
라이브러리 경로는 별도 테스트 서버의 `libraries`를 지정한다.

```bash
python3 tools/benchmark/eartopia-current/run.py \
  --server-jar shreddedpaper-server/build/libs/astatine-server-1.21.11-R0.1-SNAPSHOT.jar \
  --api-jar shreddedpaper-api/build/libs/shreddedpaper-api-1.21.11-R0.1-SNAPSHOT.jar \
  --libraries /path/to/isolated-server/libraries \
  --output run/eartopia-current-independent \
  --workloads singleton_64 same_64 descending_16 mixed_256 interleaved_256
```

API JAR 이름은 checkout의 실제 산출물에 맞춘다. `--verify-only`는 컴파일과 정확성
검사만 실행한다. `--workloads`를 생략하면 11개 작업을 모두 실행한다.
`--cpus 1,3`처럼 지정하면 서로 다른 CPU에서 최대 두 쌍을 동시에 실행할 수 있다.
기본값은 허용된 첫 CPU 하나다. 출력 디렉터리는 비어 있어야 하며, 소스와 JAR를
그 안에 복사한 뒤 컴파일한다. 입력 서버 디렉터리는 수정하지 않는다.

## 미채택 보조 경로

`fastLookup`과 `emptyEventFastPath`는 이 도구에 포함하지 않았다. 첨부의 대역
검사와 패치 클래스 컴파일은 통과했지만, 현재 서버에서 유효한 성능 개선 근거가 없다.
이벤트 리스너가 있는 실제 플러그인 환경 및 이벤트 중 회로 재진입도 확인되지 않았다.
